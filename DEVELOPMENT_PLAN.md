# План развития: от локального приложения к многоплатформенной системе

Версия документа: 1.0 (черновик на обсуждение)
Дата: 2026-09-24

## Цель

Превратить локальное Windows-приложение в систему учёта рабочего времени КФХ:

- **Платформы:** Windows (полный клиент), Android (клиент Оператора), Веб (запасной/просмотровый клиент).
- **Одна кодовая база** Flutter + один общий пакет доменной логики (расчёт ЗП) для клиента и сервера.
- **Архитектура offline-first:** каждый клиент работает с локальной БД; сервер на VPS (TimeWeb, MySQL) — единственный источник правды; синхронизация через собственный API.
- **Пользователи и роли:** Администратор, Бухгалтер, Оператор (+ периоды, аудит, закрытие месяцев).

## Ключевые архитектурные решения (фиксируются до старта)

| Решение | Выбор | Обоснование |
|---|---|---|
| Локальная БД клиента | **drift** (SQLite на Win/Android, WASM/IndexedDB в веб) | Одна схема и один код миграций на все платформы; замена sqflite |
| Ключи записей | **UUID (TEXT)** | Синхронизация между устройствами без конфликтов ключей |
| Сервер | **Собственный API на Dart (shelf)** + MySQL 8 на TimeWeb VPS | Единый язык с клиентом; общий пакет `domain` — расчёт ЗП один и тот же везде |
| Доступ к MySQL | **Только через API** (клиенты БД не трогают) | Безопасность, проверка ролей на сервере |
| Модель синхронизации | Push очереди + Pull по курсору (server-side `change_seq`), last-write-wins по `updated_at` + аудит | Мало писателей, редкие конфликты; простота и предсказуемость |
| Ввод данных | Оператор вводит за всех; работники позже получают **просмотр + подтверждение** (не редактирование) | Табель — документ работодателя; самоотчёт создаёт работу по сверке |
| Схема данных v2 | + `updated_at`, `deleted` (soft-delete), `edited_by`, `sync_seq`; таблицы `users`, `audit_log`, `period_locks`, `change_log` | Фундамент синхронизации, ролей и аудита |

## Общие правила выполнения работ

1. **Каждый этап начинается после явного подтверждения** владельца проекта.
2. Перед любым изменением схемы БД — тесты на затрагиваемую логику зелёные.
3. Перед любой миграцией данных — резервная копия БД (сейчас локальная, позже — проверка серверного бэкапа).
4. Git: одна ветка (`feature/stage-N-...`) на этап, коммиты атомарные, merge в `main` только при выполнённых критериях приёмки этапа.
5. Критерии приёмки этапа проверяются на реальных данных текущей БД (копия, не оригинал).
6. Из репозитория убираются мусорные файлы; `build/`, логи, архивы — в `.gitignore`.

## Этап 3. Синхронизация в клиенте (Windows — первый клиент) ✅ (завершён 2026-09-27)

**Цель:** два Windows-клиента обмениваются данными через сервер; офлайн-ввод не теряется.

**Решения владельца (2026-09-27):**
- на Windows в этапе 3 входят только админ и бухгалтер; оператору — понятный отказ (экраны по ролям — этап 4);
- одна и та же запись по уникальному ключу (день табеля, месяц расчёта), введённая на двух устройствах офлайн: побеждает пришедшая на сервер первой, вторая мягко удаляется локально и пишется в журнал конфликтов (расчёты ЗП — без журнала, они пересчитываются);
- второй клиент для приёмки — debug-сборка на этом же ПК под отдельной учёткой;
- полное восстановление из копии на привязанном к серверу ПК: очередь сбрасывается, данные заново принимаются с сервера (сервер — истина); вернуть старые данные на сервер — восстановлением таблиц/строк (они получают новое `updated_at`).

**Шаги**

- [x] 3.1. Очередь и применение изменений в `packages/local_db`: неотправленная запись — та, у которой `updated_at ≠ remote_updated_at` (ловит любой путь записи: DAO, просмотр базы, восстановление); `pending_changes` хранит отклонённые сервером изменения; `applyRemote` — запись пришедших изменений без постановки в очередь, LWW, освобождение уникального ключа, проигранные локальные правки — в отчёт; курсор и эпоха в `sync_state`.
- [x] 3.2. Движок `packages/sync` (транспорт HTTP с токенами, push/pull, backoff, журнал конфликтов), тесты на поддельном транспорте и на стенде.
- [x] 3.3. Первый вход: пустой сервер → выгрузка (`/admin/import`); данные совпадают по uuid → привязка; пустая локальная база → только приём; чужие данные → отказ. Перед любым — копия базы. (Копия реальной базы, импортированная на стенд, привязалась без отправок и потерь; второй ПК получил все 130 записей поле в поле, расчёт ЗП совпал.)
- [x] 3.4. Экран входа, хранение токенов, индикатор синхронизации, журнал. (Индикатор — строка состояния над нижней навигацией, по UI_REQUIREMENTS п. 2.2; токены — DPAPI Windows в файле рядом с базой вместо `flutter_secure_storage`, которому для сборки нужен ATL Visual Studio.)
- [x] 3.5. Триггеры синхронизации: при запуске, через 5 с после последней правки, раз в 5 минут, кнопка; без сети — паузы 5 с … 5 мин (`SyncScheduler`).
- [x] 3.6. Закрытые месяцы в интерфейсе: список — с сервера при каждой синхронизации; отметка «закрыт» в табеле, выплатах и отчётах; правка в закрытом месяце не записывается, с объяснением (правила — общий с сервером `PeriodGuard`, перенесён в `kfh_domain`).
- [x] 3.7. Защита боевых данных: debug — по умолчанию локальный стенд, другой сервер — только с отметкой согласия (нужен для приёмки вторым клиентом); полное восстановление на привязанном ПК — синхронизация на паузе, затем повторная сверка с сервером как при привязке, с предупреждением в окнах восстановления.
- [x] 3.8. Приёмка, версия 1.2.0 — пройдена 2026-09-27 на боевом сервере вместе с владельцем: ПК владельца (1.2.0, `ivan`) привязан к серверу без единой отправки и потери (общих записей — все, только здесь/только на сервере — 0); второй клиент (debug-сборка на том же ПК с пустой базой, учётка бухгалтера `buh`) принял 129 записей, табель совпал; «два ПК» — дни, введённые на каждом, появились на другом; «офлайн» — правка без сети ушла после подключения одним изменением; пробные дни удалены, дубликатов на сервере нет, живых записей табеля — снова 80, октябрьский расчёт после пересчёта — 0 ₽.

**Задачи**

- [ ] `packages/sync`: движок (очередь `pending_changes`, push с ретраями и backoff, pull по курсору, применение изменений в drift, разрешение конфликтов last-write-wins по `remote_updated_at`, запись проигранных конфликтов в журнал).
- [ ] Экран входа: логин/пароль, хранение токенов (`flutter_secure_storage`), смена пользователя, «автономный режим» (работа без входа = только локально, вход требуется для синхронизации).
- [ ] Индикатор синхронизации: статус, дата последней синхронизации, счётчик неотправленных, кнопка «Синхронизировать сейчас», человекочитаемые ошибки.

- [ ] **Начальный бутстрап:** первый вход клиента с существующими локальными данными → предложение «выгрузить базу на сервер» (через `/admin/import`); сервер при этом проверяет, пуст ли.

**Критерии приёмки**

- Сценарий «два ПК»: ввод на первом → синхронизация → появилось на втором, и наоборот.
- Сценарий «офлайн»: ввод без сети → повторное подключение → данные ушли, дубликатов нет.
- Текущая база успешно выгружена на сервер и видна второму клиенту.

**Оценка:** 2 недели.

## Этап 4. Android-клиент Оператора + адаптивный интерфейс

**Цель:** оператор вводит табель с телефона, офлайн; интерфейс адаптирован к платформам и соответствует UI_REQUIREMENTS.md.

**Задачи — платформа**

- [ ] `flutter create --platforms=android`; иконка, сплэш; подписание keystore (хранение ключа — вне репозитория).
- [ ] Разрешения: сеть; бэкап Android отключён или настроен осознанно (данные — в своей синхронизации).
- [ ] Дистрибуция: APK выкладывается на VPS (страница загрузки + проверка минимальной версии через API); Play Store — опционально, позже.

**Задачи — UI (один адаптивный каркас для всех платформ)**

- [ ] Каркас: телефон — нижняя навигация; планшет/десктоп/веб — `NavigationRail`/боковая панель (стандарт п. 2.2).
- [ ] Режим по роли: Оператору доступны только табель (своих сотрудников при бригадах) и просмотр; меню не просто скрыто, но и сервер отвергает чужие действия.
- [ ] Экран «ввод за день»: крупные ячейки-кнопки, одиночный тап (двойной тап заменён везде), минимум диалогов, работа одной рукой.
- [ ] Сетка табеля: Sticky-заголовки, горизонтальный скролл, тап вместо двойного тапа (стандарт п. 1.1).
- [ ] Диалоги → bottom sheets на телефоне.
- [ ] Windows-оболочка: минимальный размер окна 1024×768, сохранение геометрии/разворота между запусками, показ окна после расчёта раскладки (стандарт п. 2.1).

**Критерии приёмки**

- Оператор на телефоне вводит день офлайн в поле → при появлении сети данные уходят сами.
- Попытка оператора открыть выплаты/настройки невозможна в UI и отвергается сервером.
- Установка APK «с нуля» → вход → данные подтянулись с сервера.

**Оценка:** 1,5–2 недели.

## Этап 5. Веб-клиент

**Цель:** та же кодовая база в браузере; запасной вход для бухгалтера/админа, будущая точка просмотра для работников.

**Задачи**

- [ ] `flutter create --platforms=web`; drift → WASM/IndexedDB (тот же `local_db`-пакет).
- [ ] Сборка и деплой статических файлов через Caddy на том же VPS (единый домен: `/` — веб, `/api` — API).
- [ ] Печать из веб: `pdf` формирует документ, `printing` открывает превью/скачивание; проверка кириллицы.
- [ ] Авторизация как в приложении; автоматический выход по истечении refresh-токена.
- [ ] Проверка офлайн-поведения: ввод при пропавшей сети в открытой вкладке — данные в IndexedDB, синхронизация после восстановления.
- [ ] Определение минимальной версии клиента на всех платформах: API отдаёт `min_client_version`, клиент при устаревании показывает экран «обновитесь».

**Критерии приёмки**

- Веб открывается с телефона и ПК, логин, просмотр/ввод табеля, печать PDF с кириллицей.
- Данные, введённые в веб, видны в Windows-клиенте после синхронизации, и наоборот.

**Оценка:** 1–2 недели.

## Риски и их обработка

| Риск | Вероятность | Мера |
|---|---|---|
| Потеря VPS/MySQL без бэкапа | низкая, удар максимальный | Ежедневный дамп + копия вне VPS (этап 2, неп negotiable) |
| Конфликты правок при синхронизации | средняя | LWW + аудит; закрытие периодов резко сужает окно правок |
| «Кто-то не обновил клиент» | средняя | `min_client_version` в API, жёсткое требование обновления |
| Расхождение расчёта ЗП между платформами | исключено конструктивно | Единый `domain`-пакет у клиента и сервера |
| Человек забыл пароль оператора | высокая | Сброс паролем админа (этап 2) |
| Сломанная миграция на боевых данных | средняя | Миграция тестируется на копии реальной базы (этапы 0–1), откат = восстановление бэкапа |
| TimeWeb-специфика (порты, Docker) | низкая | Всё в Docker Compose, переносимо на любой VPS |

## Открытые вопросы (нужны решения владельца до/в процессе)

1. **Бригадиры:** нужны ли подмножества сотрудников для операторов (несколько операторов на бригады) — закладываю в схему `users`, включаю в этап 4 только при подтверждении.
2. **Подтверждение работниками:** канал — веб-страница, Telegram-бот или оба (этап 6).
3. **Дистрибуция Android:** прямой APK с VPS (рекомендую) или публикация в RuStore/Play.
4. **Домен:** есть ли домен для HTTPS, или использовать временный (TimeWeb выдаёт поддомены).
5. **Хранилище внешних бэкапов:** S3-совместимое (Timeweb Cloud имеет) / Яндекс.Диск / скачивание на ПК владельца.
