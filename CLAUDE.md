# CLAUDE.md

Учёт рабочего времени и расчёт ЗП для небольшого КФХ. Flutter (Windows, Android, веб), SQLite через drift (пакет `packages/local_db`), состояние — `provider`.
Владелец проекта один, он же пользователь. Общение, комментарии в коде и коммиты — **на русском**.

## Архитектура

- Dart workspace: корневой `pubspec.yaml` перечисляет `packages/*` в `workspace:`, у пакетов `resolution: workspace`, `pubspec.lock` один — в корне.
- `packages/domain` (пакет `kfh_domain`, импорт `package:kfh_domain/kfh_domain.dart`) — чистый Dart без Flutter и БД: модели, расчёт ЗП (`calculateMonthlySalary`, `findRateAtDate`, `combineBalances`), `date_utils`. Новую бизнес-логику класть сюда и покрывать тестами (`dart test`). Там же интерфейсы репозиториев (`repositories.dart`, `DuplicateEntryException`) и `PayrollService` (расчёт месяца и входящие остатки поверх репозиториев). Id моделей — `String` (uuid). У моделей нет `toMap`/`fromMap`: преобразование в строки базы — в `DriftRepositories`. Снять увольнение — `copyWith(clearDismissalDate: true)` (`dismissalDate: null` в copyWith значит «не менять»).
- `packages/local_db` (пакет `kfh_local_db`) — чистый Dart: схема v2 на drift (`LocalDatabase`, таблицы в `lib/src/tables/tables.dart`) и DAO; `DriftRepositories` — реализация репозиториев домена. Ключ `uuid` (v7), поля `legacy_id`, `updated_at` (UTC, текстом ISO), `deleted`, `edited_by` (id устройства из `sync_state`), `remote_updated_at`. DAO сами ставят `updated_at`/`edited_by`, удаление мягкое, чтения фильтруют `deleted = 0`. Внешние ключи отложенные, уникальные индексы частичные (`WHERE deleted = 0`). Версия drift-схемы — 1 (новый файл, не миграция v8). drift и drift_dev закреплены на 2.34.0: новее не сходится с Flutter 3.44 (analyzer).
- Синхронизация в клиенте (`packages/local_db/lib/src/sync/local_sync_store.dart`, `LocalSyncStore`): запись не отправлена, если `updated_at ≠ remote_updated_at` (текстовое сравнение) — очередь сама ловит любой путь записи, отдельно её вести не нужно. `pending_changes` хранит только отклонённые сервером правки (не уходят повторно, пока запись не изменят или не вызовут `clearRejections`). `applyRemote` пишет с `remote_updated_at = updated_at` (в очередь не попадает): чистая запись принимает серверную версию, неотправленная новее — остаётся, старше или равная — уступает (`ApplyReport.lost`); живая запись с тем же уникальным ключом снимается без новой версии (`_markDeletedSynced`), при риске расхождения — `needsResync` (pull с нуля). Курсор и эпоха — `sync_state` (`sync_cursor`, `sync_epoch`). Своя же версия, вернувшаяся с сервера, не переписывается (`ApplyReport.unchanged`). В новой базе строка настроек хозяйства сразу «не отправлена» — при первом входе на пустом ПК сначала `markAllSynced()`, иначе умолчания уйдут на сервер. Курсор страницы pull сохраняется в той же транзакции, что и её записи (`applyRemote(cursor:)`).
- `packages/sync` (пакет `kfh_sync`, чистый Dart без dart:io; файловый журнал — отдельно, `package:kfh_sync/file_journal.dart`): `KfhApiClient` — вход, токены (`TokenStore`; access обновляется заранее и после `token_invalid`, refresh — строго по одному, т.к. одноразовый), ошибки — `SyncFailure` (`NetworkFailure`/`ServerFailure` — временные, `ApiFailure` с кодом сервера, `needsLogin`; `NotSignedIn`). `SyncEngine.run()` — push пачками, затем pull до конца; `stale` — ждёт pull, `unique_conflict` — `discardLocal` + журнал (кроме расчётов ЗП), прочие отказы — `markRejected`; `resync_required` и `needsResync` — pull с нуля; временные сбои повторяются внутри прогона, дальше — исключение (пауза между прогонами — `Backoff`, 3.5); один прогон одновременно. Первый вход — `SyncBootstrap` (3.3): `analyze(user)` только читает (uuid всех записей сервера постранично против `localKeys()`, без строки настроек) → план `upload` (сервер пуст, только админ; `/admin/import`, затем обычный прогон — сплошь `duplicate`) / `link` (есть общие записи) / `download` (здесь пусто; `markAllSynced`) / `fresh` / `foreign` (нет общих записей — отказ); `execute(plan, backup:)` — без копии не начинается, если база привязана не к этому серверу — `forgetServer()`, затем `engine.run(linking: true)` и `setLinkedServer`. Прерванный первый вход безопасно повторяется. При привязке все записи «не отправлены», поэтому уступившая серверу версия — не обязательно правка: журнал пишет это без упрёка (`linking`). Журнал конфликтов — `SyncJournal` (JSON-строки, `FileSyncJournal` с ротацией в `.1`). Тесты движка — на `test/support/fake_server.dart` (правила как у `SyncService`); сквозной тест с настоящим сервером и MySQL — `server/test/client_sync_test.dart` (обработчик API в процессе, без сети), поэтому `kfh_sync` и `drift` — dev-зависимости сервера (и в `server/Dockerfile` — pubspec пакета).
- `packages/local_db/lib/src/schema_info.dart` — списки бизнес-таблиц, поля-даты, служебные поля, уникальные ключи. `raw_tables.dart` (`RawTables`) — просмотр и правка таблиц «как есть»: правка ставит `updated_at`/`edited_by`, служебные поля не правятся, удаление мягкое и обратимое, служебные таблицы — только чтение. `backup_restore.dart` — `detectBackupFormat` (v8/v2), `prepareFullRestore` (файл v2 из копии любого формата, v8 — через конвертер; id устройства сохраняется), `BackupRestorer` (таблицы и строки — только из копий v2, по uuid, с новым `updated_at`; занятый день табеля/месяц расчёта освобождается мягким удалением).
- Конвертер `convertV8ToV2` (`packages/local_db/lib/src/migration/v8_converter.dart`): принимает только базу `user_version = 8`, старый файл открывает только на чтение, пишет в `<цель>.tmp`, сверяет все поля всех строк через `legacy_id` и пересчёт ЗП за каждый месяц, делает `integrity_check`/`foreign_key_check`, затем переименовывает файл. Если цель уже есть — отказ. Прогон на копии: `dart run tool/convert_v8.dart <v8.db> <v2.db>` в `packages/local_db`.
- `server/` (пакет `kfh_server`, член workspace) — API на `shelf` + MySQL (`mysql_client_plus`, TLS, utf8mb4). Пул соединений свой (`server/lib/src/pool.dart`): пул пакета после ошибки возвращает закрытое соединение (сервер не оживает после перезапуска MySQL) и теряет соединения при исключении — его `MySQLConnectionPool` не использовать. Миграции — `server/migrations/NNNN_имя.sql` + свой раннер (`schema_migrations`, sha256, `GET_LOCK`); сервер без применённых миграций не стартует, `server migrate` применяет. DDL в MySQL не транзакционен — перед миграцией только резервная копия. Схема MySQL повторяет клиентскую, `server/test/schema_test.dart` сверяет её со снимком drift: при изменении таблиц клиента нужна миграция сервера. Результаты MySQL читать только через `row.text()`/`textOf()` из `server/lib/src/sql.dart` (драйвер отдаёт столбцы `_bin` байтами, JSON — объектами), моменты времени в параметры — `sqlDateTime()`. Вход (`server/lib/src/auth/`): Argon2id, JWT HS256 15 мин + refresh 30 дней с ротацией, пользователь читается из базы на каждый запрос; действия — в `audit_log` в той же транзакции. Синхронизация (`server/lib/src/sync/`): формат — `SyncChange`/`syncTables` в `kfh_domain` (`packages/domain/lib/src/sync/`, сверяется тестами с drift и MySQL; при изменении таблиц править и его), push — одна транзакция под блокировкой `sync_serial` (любой писатель `change_log` обязан брать `ChangeLog.lock`), last-write-wins по `updated_at`, закрытые месяцы — `PeriodGuard` (в `kfh_domain`, `packages/domain/lib/src/sync/period_guard.dart`: те же правила проверяет клиент); pull по курсору `seq` + эпоха (после восстановления из копии — `UPDATE sync_serial SET epoch = UUID()`). Расчёт ЗП на сервере (`server/lib/src/payroll/`) — только через чистые функции `kfh_domain`, пишет изменившиеся расчёты с `edited_by = server`; закрытые месяцы — `server/lib/src/periods/` (остатки по месяцам для предпросмотра открытия и снимков — `period_balances.dart`); чтение для веба — `DataApi`. Разовый импорт базы устройства — `POST /admin/import` (`server/lib/src/admin/import_service.dart`): только админ, только в пустую базу, одна транзакция со сверкой (записи поле в поле, расчёт и остатки против контроля выгрузки) до COMMIT. Выгрузка — `SyncExport` (`kfh_domain`), строится `buildSyncExport` в `packages/local_db/lib/src/sync/sync_export_builder.dart` (там же `syncChangeFromLocalRow` — строка drift → формат обмена, пригодится движку синхронизации этапа 3). Настройки только из переменных окружения (`ServerConfig`), журнал — JSON-строки в stdout, ошибки API — `{"error":{"code","message"}}` (`ApiException`), у ответа `X-Request-Id`. Версия — `server/pubspec.yaml` и `lib/src/version.dart` (сверяет тест). Образ — `server/Dockerfile` из корня репозитория: внутри собирается свой workspace (domain + server), т.к. корневой pubspec требует Flutter. Подробности — `server/README.md`.
- `lib/services/app_database.dart` — `openAppDatabase` в `main.dart` до `runApp`: если `kfx_time_tracking_v2.db` нет, находит старую базу v8 (`db_location.dart`), делает её копию `backup_v8_<дата-время>.db` и переносит конвертером в `Isolate.run`. Без копии перенос не начинается. Если перенос не прошёл — `StartupErrorApp` с причиной, ни одна база не открыта, старая не тронута, при следующем запуске повтор. `AppDatabase` = `LocalDatabase` + `DriftRepositories` + путь. Полное восстановление (`AppProvider.restoreFullBackup`): копия текущей базы `backup_before_restore_…` → файл `.restore` в `Isolate.run` → закрыть базу → `replaceDatabaseFile` (старый файл через `.old`) → переоткрыть. Любое восстановление начинается с копии текущей базы.
- Синхронизация в приложении (3.4): `lib/providers/sync_provider.dart` (`SyncProvider`, фазы `signedOut`/`passwordChange`/`needsLink`/`ready`; сервер по умолчанию: release — `https://tab.korovatech.ru`, debug — `http://localhost:8080`; вход только админа/бухгалтера; ошибки — понятным текстом в `problem`, `SyncUserException`; после приёма данных — `AppProvider.reloadAfterSync`; копия перед первым входом — `backup_before_sync_<дата-время>.db`; время последней синхронизации — `sync_state.sync_last_at`; журнал — `sync.log` рядом с базой; при полном восстановлении база переоткрывается — `databaseGeneration` → `rebind`). Оба провайдера создаются в `_MyAppState` (`main.dart`). Интерфейс: `SyncStatusBar` над нижней навигацией (`main_screen.dart`), `lib/widgets/sync_dialogs.dart` (вход, смена пароля, первый вход — `startSignIn`/`continueSyncSetup`), `lib/screens/sync_screen.dart` (Настройки → Сервер синхронизации: учётная запись, отклонённые правки, журнал). Токены — `lib/services/dpapi_token_store.dart`: файл `sync_auth.dat` рядом с базой, DPAPI (CryptProtectData) через `win32`/`ffi`; `flutter_secure_storage` не подошёл — его Windows-плагину для сборки нужен компонент ATL Visual Studio. Автоматика (3.5) — `SyncScheduler` в `packages/sync` (при запуске сразу, через 5 с после последней правки, раз в 5 минут; после временного сбоя — `Backoff` 5 с…5 мин, правки повтор не ускоряют; нужен вход — стоп до `resume`; кнопка — `ranManually`); в `SyncProvider` включена по умолчанию (`autoSync`, в тестах интерфейса выключают), запускается в фазе `ready`. Правка человека определяется по `tableUpdates()` бизнес-таблиц вне прогона синхронизации и при `pending > rejected` — записи самой синхронизации её не перезапускают. Закрытые месяцы (3.6): список приходит с `GET /periods/locks` после каждой удачной синхронизации (`KfhApiClient.lockedMonths`, `LocalSyncStore.saveLockedMonths` → `sync_state.period_locks`, `onLocksChanged` → `AppProvider.loadLockedMonths`). `AppProvider` не записывает правку, задевающую закрытый месяц (`PeriodGuard` на те же поля: табель, выплаты, расчёт, ставки), и кладёт объяснение в `takeNotice()` — `MainScreen` показывает его внизу окна; экраны табеля, выплат и отчётов — отметка `ClosedMonthBadge` и `ensureMonthOpen` до открытия правки (`lib/widgets/closed_month.dart`). Список устаревает до следующей синхронизации — окончательно решает сервер (отказ → «не принято сервером»). Закрытие и открытие месяцев (6.2): `SyncProvider.lockMonth` (сначала синхронизация, неотправленная правка в месяце — отказ, `LocalSyncStore.pendingInMonth`; затем `KfhApiClient.lockMonth`, затем синхронизация) и `unlockMonth` (только админ; сначала `unlockPreview` — сервер показывает изменения остатков, админ подтверждает; сервер сохраняет снимок «до» в `period_snapshots`, снимки — `periodSnapshots`/`periodSnapshot`, сравнение снимка с расчётами сейчас — `periodSnapshotChanges` (таблица «было/стало» — `BalanceChangesTable`); после — `syncNow(retryRejected: true)`; всё это — только на сервере не ниже `periodServerVersion` 0.4.0), права — `canLockMonths`/`canUnlockMonths`; окна — `lib/widgets/period_lock_dialogs.dart` (`closeMonth`/`openMonth`), экран — `lib/screens/periods_screen.dart` (Настройки → Закрытие месяцев), замок в отчёте. Защита (3.7): debug-сборка входит на сервер не на этом компьютере (`SyncProvider.isLocalServer`) только с отметкой согласия в окне входа (`allowRemoteInDebug`, у debug своя база — смешать данные не даст первый вход). ## Доменные правила

- Табель: `dayType` = `work` | `sick` | `vacation` | `dayoff`; для `work` значение `days` равно 1 или 0.5, `workPlace` = `base` | `field`.
- Ставка действует на дату, если `start_date <= дата <= end_date` (`end_date = null` — бессрочно). Новая ставка закрывает предыдущую датой «начало − 1 день».
- Управление ставками (доработка этапа 5, решение владельца 2026-09-28): в списке сотрудников и форме сотрудника — текущие ставки (действующие сегодня, из истории, `AppProvider.currentRate`), правка — только на экране «Ставки» (`employee_rate_history_screen.dart`): добавить с любой даты, изменить суммы/начало (между соседями)/окончание (только у последней), удалить (период переходит к предыдущей, если та шла вплотную). Логика — чистые функции `planAddRate`/`planUpdateRate`/`planDeleteRate` в `packages/domain/lib/src/rate_timeline.dart` → список `RateChange` → проверка `PeriodGuard` по каждой правке → `RateRepository.apply` одной транзакцией. Меняются только затронутые соседи. `employees.base_rate/field_rate` — копия текущей ставки (её обновляет `AppProvider`, форма сотрудника ставки не пишет), первая ставка — при добавлении сотрудника.
- Рабочий день без ставки не оплачивается, а учитывается в `skippedWorkDays`.
- Остаток = начислено за прошлые месяцы − выплачено до 1-го числа месяца.
- Расчёты ЗП (6.1, решение владельца 2026-09-28): сохранённые расчёты пишет только сервер — после каждой принятой правки пересчитывает открытые месяцы (`PayrollCalculator.recalculateOpenMonths`, с месяца `payrollImpactFrom`), а также при открытии месяца и при запуске. Закрытый месяц не пересчитывается никогда. Приложение расчёты не сохраняет: отчёт — `PayrollService.monthReport` (открытый месяц — свежий пересчёт, закрытый — зафиксированный расчёт + `differs`), остаток — `currentBalances` (закрытые месяцы — по зафиксированному, открытые — по пересчёту). `startingBalances` (по сохранённым) и `saveMonth` остались для выгрузки/импорта и сверок.
- В расчёт месяца и в отчёт входят только сотрудники, у которых в месяце есть начисления (дни работы, больничного, отпуска, неоплаченные дни без ставки или сумма) или выплаты, либо ненулевой входящий остаток на 1-е число (от полкопейки; `payrollNeeded` в `packages/domain/lib/src/payroll.dart`, решение владельца 2026-09-26). Пустой расчёт не сохраняется, ставший пустым — удаляется при пересчёте (`PayrollService.saveMonth`); отчёт скрывает пустые строки, оставшиеся от старых расчётов (`resultsForReport`). Сервер следует тому же правилу.
- Даты в БД хранятся строками ISO `гггг-мм-дд` (`packages/domain/lib/src/utils/date_utils.dart`). День в программе — местная полночь; момент в UTC — не день: его день берётся по местному календарю (`calendarDay`, `parseDateIso` для значений с `Z`/смещением). Сдвигать дни — только `addCalendarDays`/`DateTime(г, м, д ± n)`, не `Duration(days: n)` (в день перевода часов сутки не 24 часа). «Работает на дату» — `Employee.isActiveOn`: день увольнения уже нерабочий, время суток не влияет.
- `AppProvider.calculateMonthlySalary`/`calculateSingleEmployeePayroll` возвращают `PayrollCalculation.toMap()` с прежними ключами — экраны зависят от них.

## Правила работы

- Развитие идёт по этапам из `DEVELOPMENT_PLAN.md`. **Каждый этап — только после явного согласия владельца**, в ветке `feature/stage-N-...`.
- Требования к интерфейсу — `UI_REQUIREMENTS.md` (читать при работе над экранами, а не целиком каждый раз).
- Любое изменение схемы БД или миграция — только после свежей резервной копии и на копии реальной базы. Боевую базу не трогать.
- Боевая база — `%LOCALAPPDATA%\KFH Time Tracking\kfx_time_tracking.db` (v8), после первого запуска версии с drift — `kfx_time_tracking_v2.db` рядом. `flutter run` (debug) работает с отдельной базой в `KFH Time Tracking (debug)` и отдельной папкой копий. Релизный exe из инструментов Claude не запускать: он найдёт настоящую базу.
- Claude desktop — MSIX-приложение: записи его инструментов в `%LOCALAPPDATA%` виртуализируются в `%LOCALAPPDATA%\Packages\Claude_*\LocalCache\`, другим программам они не видны, а при чтении виртуальная копия заслоняет настоящую. К настоящей AppData обращаться через `\\localhost\C$\Users\<пользователь>\AppData\Local\...`. `Документы` не виртуализируются.
- Перед коммитом: `flutter analyze`, `flutter test` и `dart test` в `packages/domain`, `packages/local_db` и `server` зелёные (для сервера — ещё `dart analyze` в `server/`). То же на каждый push проверяет CI (`.github/workflows/ci.yml`, этап 6.3): приложение — на Windows, пакеты и сервер — на Linux с MySQL; `gh` нет — результат смотреть через API GitHub (`/repos/likafarm/timesheet_kfh/actions/runs`, репозиторий открытый) или страницу Actions во встроенном браузере.
- `build_installer.ps1` держать в ASCII (транслит): Windows PowerShell 5.1 читает UTF-8 без BOM как ANSI.
- Рабочие файлы в LF, Git конвертирует их в CRLF — это нормально.
